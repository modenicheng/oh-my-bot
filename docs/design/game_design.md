可以先把它冻结成一套相对完整的 v0.1。核心定位不是“编程竞赛”，而是：

> **64 人实时机器人派对大乱斗。任何人都能手操开打，随后逐渐用 Snippet、AI 或代码接管自己的机器人。**

编程提高上限，但不构成入场门槛。

## 1. 一局到底在干什么

建议单局约 8 分钟，64 人同时进入一张俯视角二维竞技场。每个人只有一台机器人，不造兵、不采矿造基地、不经营科技树。

玩家不断在三个事情之间选择：

> 抢资源 → 抢区域 → 和其他机器人互殴

死亡不是淘汰，几秒后复活。因此不存在“小白一分钟暴毙，然后看别人玩七分钟”。

游戏过程中规则会阶段性变化，但基础操作始终不变。例如：

| 时间 | 阶段 | 主要变化 |
|---|---|---|
| 0:00–1:30 | 自由行动 | 熟悉地图、捡资源、小规模冲突 |
| 1:30–3:00 | 区域争夺 | 若干控制点激活 |
| 3:00–4:30 | 临时组队 | 随机分成 4 队或 8 队 |
| 4:30–6:00 | 世界事件 | Boss、资源雨、移动目标等 |
| 6:00–7:00 | 双人搭档 | 两人临时协作 |
| 7:00–8:00 | 最终乱斗 | 高价值目标全部激活 |

不必每局固定这个顺序，房主以后可以选规则集。

这样大佬没法写一套 `nearestEnemy -> shoot()` 后挂机八分钟，因为游戏目标会变化；小白则只需要看屏幕上当前出现什么，就知道下一步该去哪。

## 2. 地图：不要做成空旷圆形竞技场

64 人如果放在一块空地上，体验会迅速变成弹幕地狱。

我更倾向于一个大约这样的逻辑结构：

```text
┌───────────────────────────────────────┐
│ Spawn      外围资源区        Spawn    │
│   ┌─────┐            ┌─────┐         │
│   │     ├────┐  ┌────┤     │         │
│   └─────┘    │  │    └─────┘         │
│              ▼  ▼                     │
│          ┌──────────┐                 │
│   中区 ──┤   中央   ├── 中区          │
│          │ 高价值区 │                 │
│          └──────────┘                 │
│              ▲  ▲                     │
│   ┌─────┐    │  │    ┌─────┐         │
│   │     ├────┘  └────┤     │         │
│   └─────┘            └─────┘         │
│ Spawn                       Spawn    │
└───────────────────────────────────────┘
```

地图最好形成三层风险梯度。

外围区域比较安全，资源少，适合刚进游戏、小白熟悉操作。中部开始有争夺目标和较多资源。中央最危险，但奖励最高，世界事件通常也发生在这里。

地图内部不要全是墙，而应该存在矮墙、狭窄通道、开阔区域、环形路线、单向跳板、传送门等非常容易理解的元素。

这样一台只会：

```js
moveTo(nearestCore())
```

的傻机器人也可能正常玩。

而高手则可以开始研究：

```text
绕墙
卡射线
逃跑路线
控制距离
伏击
预测目标区域
```

地图本身就自然提供算法深度。

## 3. 64 人不能只有一个出生点

建议地图外围有 8 个出生区域，每个区域大约 8 人。

死亡后也不要原地复活，而是在相对安全的出生区域重新生成，并附带短暂无敌。

更重要的是避免形成：

```text
强者杀人
→ 得到强化
→ 更容易杀人
→ 继续强化
```

所以击杀最好主要提供分数，而不是永久战斗属性。

机器人战斗能力在整局中应基本固定。

这样新手第七分钟复活出来，仍然有能力干掉排行榜第一，而不是面对一个 HP × 5、伤害 × 4 的怪物。

# 4. 玩家控制的机器人

我建议外形也是“一个主体 + 明确朝向”，不要做人形机器人。

例如：

```text
       SENSOR
         ◉
      ┌───────┐
  ◄── │  BOT  │ ──► 炮口
      └───────┘
        ╱   ╲
```

原因很简单：**代码非常容易理解它。**

机器人最基础状态可以只有这些：

| 状态 | 含义 |
|---|---|
| position | 坐标 |
| direction | 朝向 |
| velocity | 当前运动状态 |
| hp | 生命 |
| energy | 能量 |
| shield | 护盾状态 |
| cooldown | 武器状态 |
| score | 当前得分 |

不要出现几十个属性。

初版机器人也不要装备系统、技能树、背包、枪械换装。

复杂度应该来自**如何控制机器人**，而不是研究 RPG 装备表。

---

# 5. 基础动作

机器人初期可以控制在七个核心能力：

```text
移动
转向
扫描
射击
冲刺
护盾
交互
```

外加一个不影响战斗的：

```text
say()
```

`say()` 我觉得必须有。

例如程序可以：

```python
if enemy:
    say("你完了")
    fire(enemy)
```

然后地图上机器人头顶真的冒出：

```text
┌ 你完了
🤖
```

破冰场景里，这种功能价值可能比某个高级战斗机制还高。

当然要限频。

---

# 6. 移动不应该做成格子游戏

Screeps 本质非常格子化。

这里我更推荐连续二维运动：

```text
x = 43.7
y = 28.1
direction = 1.24 rad
```

手操玩家体验更像普通 `.io` 游戏。

WASD 控制方向或者运动，鼠标控制瞄准。

程序则可以暴露更高层 API：

```js
move("forward")
moveTo(position)
turn(angle)
turnTo(entity)
```

这样小白不用学向量就能玩。

高手以后如果愿意，可以自己根据：

```js
self.position
enemy.position
```

算路线和角度。

也就是说 API 同样存在“低地板，高天花板”。

---

# 7. 战斗系统应该非常克制

我不建议一开始搞十几种武器。

机器人默认只有一种主武器，例如短冷却能量炮。

射击不是 hitscan 无限距离激光，而是一枚有飞行时间的弹丸。

于是：

```text
看到敌人
≠
一定打中敌人
```

高手可以预测移动：

```text
target.position
+ target.velocity * projectileTravelTime
```

小白则瞄着人点鼠标，也能打。

这一个设计就已经产生很大技术空间。

冲刺则用来：

```text
追杀
逃跑
闪弹
抢资源
```

护盾负责提供一个极容易理解的防御按钮。

三者共用 Energy：

```text
射击 → 消耗
冲刺 → 消耗
护盾 → 持续消耗
扫描增强 → 消耗
```

所以程序不能无脑：

```js
shield(true)
fire()
dash()
scan()
```

永久全开。

---

# 8. 扫描机制很关键

这里可以成为机器人编程最重要的玩法之一。

手操玩家直接通过屏幕看到附近东西，不需要理解雷达系统。

代码玩家则获得：

```js
scan()
```

例如：

```js
{
    robots: [...],
    cores: [...],
    objectives: [...],
    obstacles: [...]
}
```

但只能获得传感器范围内信息。

这样一个最小程序就是：

```js
const enemy = scan().nearestEnemy;

if (enemy) {
    fire(enemy);
}
```

而高手会逐渐出现：

```text
记忆敌人最后位置
预测运动
分类目标
威胁评估
跟踪多个目标
路径规划
```

因此“感知 → 决策 → 行动”本身成为整个编程玩法核心。

---

# 9. 资源设计

地图可以周期性生成一种非常简单的东西：

```text
◆ Energy Core
```

碰到后获得分数，并恢复一部分能量。

仅此一种就够第一版使用。

这样资源既是：

```text
分数来源
续航来源
争夺目标
移动诱因
```

不需要再设计金币、水晶、弹药、木头之类五六种资源。

高级事件可以生成：

```text
◆◆◆ Mega Core
```

然后全图提示：

> 中央区域出现高能核心。

六十多个机器人一起往中央冲，节目效果自然出来。

---

# 10. 占点不是“站着别动”

传统占点很无聊。

可以设计成一个节点：

```text
      ╭─────╮
      │  ◉  │
      ╰─────╯
```

玩家进入一定范围后持续产生积分。

但节点隔一段时间会：

```text
关闭
移动
换位置
```

因此机器人程序不能永远蹲一个位置。

甚至可以出现移动目标：

```text
◉ → → →
```

变成跟车式争夺。

---

# 11. 世界事件是派对感主要来源

正常机器人战斗只是底层系统。

真正让一局不无聊的应该是偶发事件。

比如：

```text
资源雨
中央 Boss
安全区收缩
移动控制点
低重力
所有机器人移速 ×1.5
护盾失效 20 秒
随机双人绑定
四阵营战争
```

不过这里要克制。

游戏第一版只需要三四种，而且事件必须一眼看懂。

不应该出现：

> “当前量子干扰使第三类技能恢复速率降低 17%。”

这种东西。

---

# 12. 双人绑定尤其适合破冰

例如某个阶段：

```text
你和 Alice 成为临时搭档
```

两个人名字旁边出现同一个图标：

```text
🤖 modenicheng   🔗   Alice 🤖
```

你们：

```text
互相无法伤害
共同获得击杀积分
靠近时获得少量能量恢复
```

甚至提供：

```js
partner()
```

然后程序员会写：

```python
if distance(self, partner) > 10:
    move_to(partner)
```

小白则直接看地图找自己队友。

这是真正将“编程”和“破冰”联系起来的机制。

---

# 13. 手操、辅助代码和全自动不是三个游戏模式

这一点应该写进核心设计。

它们实际上是同一个输入仲裁系统：

```text
        玩家输入
           │
           ▼
     ┌────────────┐
     │ Control    │
     │ Arbitration│
     └─────┬──────┘
           ▲
           │
         代码
```

例如玩家按：

```text
W
```

代码同时说：

```text
move(left)
```

需要定义规则。

我建议默认：

> **人类输入优先。**

也就是玩家随时可以“抢方向盘”。

代码则可以控制玩家当前没有控制的东西。

例如：

```text
玩家：WASD 控制移动
程序：自动瞄准 + 射击
```

或者：

```text
玩家：什么都不做
程序：完全控制机器人
```

这就是我们之前说的“驾驶辅助”。

它应该成为整个产品最有特色的部分。

---

# 14. Snippet 本质也是“安装驾驶辅助”

例如右侧不是一堆编程语法模板，而是：

| Snippet | 行为 |
|---|---|
| 自动射击 | 自动攻击视野内最近敌人 |
| 紧急护盾 | HP < 30 时开盾 |
| 自动捡资源 | 没敌人时寻找最近 Core |
| 防撞墙 | 即将碰撞时自动转向 |
| 跟随队友 | 与搭档保持距离 |
| 自动跑路 | 残血时远离最近敌人 |

因此完全不会编程的人可以先：

```text
[✓] 自动射击
[✓] 紧急护盾
[ ] 自动移动
```

然后开始玩。

他其实已经构造了一个简单控制程序，只是还没写代码。

点：

> 查看代码

才看到：

```js
if (hp < 30) {
    shield();
}
```

这个方向比一开始把 Monaco 怼到脸上好很多。

---

# 15. AI Agent 是第四种控制层

于是完整体验不是：

```text
手操 / 编程
```

而是：

```text
手操
  ↓
行为组件
  ↓
AI 帮写
  ↓
自己写
```

而且允许来回移动。

例如小白：

> “让它看到别人就打，但是不要追人。”

Agent 改代码。

机器人开始运行。

玩家：

> “这个太怂了，还是追吧。”

Agent 再修改。

高手则可能完全关掉 AI，直接 C++。

所以所有玩家最终仍然在玩**同一套机器人系统**。

---

# 16. 得分设计

总分最好由几个非常直观的来源组成：

```text
Core        +10
占点         +持续得分
造成伤害     +少量
助攻         +较多
击毁         +奖励
世界事件     +大量
```

但不必给玩家展示复杂计算公式。

屏幕上只需要不断出现：

```text
+10 Core
+20 Assist
+5 Control
```

即时反馈非常重要。

---

# 17. 结算才是真正的“破冰页面”

结束后不要直接：

```text
第 1 名
第 2 名
……
第 64 名
```

可以先展示全局：

```text
本局机器人互相发射了 18,274 发炮弹
一共撞墙 932 次
AI 修改代码 417 次
产生了 71 次自爆
```

然后展示各种称号。

例如：

| 称号 | 判定 |
|---|---|
| 战争机器 | 击毁最多 |
| 垃圾佬 | Core 最多 |
| 跑路大师 | 移动距离最长 |
| 铁头娃 | 撞墙最多 |
| 苟王 | 最长连续存活 |
| 和平使者 | 高积分但没有击毁 |
| 人工智障 | 脚本异常/超时最多 |
| 弹幕大师 | 射击最多 |
| 最佳搭档 | 双人阶段协作得分最高 |

最后才放总分。

这样 64 人里很多人都会在结果页出现一次。

# 18. 我现在会冻结的机器人规格

第一版可以非常明确：

```text
Robot

HP       100
Energy   100

Move
Turn

Primary Fire
Dash
Shield

Scan
Interact
Say
```

没有：

```text
装备系统
职业
英雄技能
科技树
等级
永久升级
库存
制作
建筑
多个单位
```

这些以后都能加。

但第一版越少越好。

因为我们真正想验证的是：

> **“手操 → 自动化 → AI → 编程”这条梯子本身，好不好玩。**

---

最后，整个游戏循环可以压缩成一句：

```text
进入房间
  ↓
立刻 WASD 玩
  ↓
发现自己忙不过来
  ↓
给机器人安装自动行为
  ↓
看见代码
  ↓
让 AI 修改
  ↓
自己开始改
  ↓
规则突然变化
  ↓
继续调程序 / 手动救场
  ↓
和其他 63 台机器人互坑
  ↓
赛后看离谱统计
```

这时我认为项目已经有一个很清楚的身份了：

**不是 Screeps Lite，也不是在线 OJ 套一个游戏皮，而是一款以“逐渐把自己的操作自动化”为核心乐趣的 64 人机器人派对游戏。**

下一步最值得继续细化的是**机器人战斗模型 + 地图几何**，因为这两个会决定“手操是否真的好玩”和“写代码是否真有策略空间”。
