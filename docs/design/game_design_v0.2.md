同意。这里需要把玩法从“频繁变规则”改成“**规则稳定，战场态势变化**”。

我建议直接冻结成：**8 分钟一局，只在 4:00 发生一次大转段；`scan()` 作为免费基础感知，不再消耗战斗资源。**

### 一、整局结构：只有两个阶段

前 4 分钟叫“外环争夺”，后 4 分钟叫“核心解锁”。

前半场中央区域关闭，64 人分散在地图外围和中环，玩家有充足时间手操、装 Snippet、让 Agent 改代码、测试机器人行为。

4:00 时中央闸门打开，高价值资源和主目标出现。之后一直打到结束。

关键在于：**转段不改变战斗规则。**

```text
0:00 ─────────────── 4:00 ─────────────── 8:00
      外环争夺              核心解锁
         │                     │
         │      只切一次       │
         └─────────────────────┘

move / fire / shield / scan / dash
整个 8 分钟完全相同
```

所以一个第一分钟写出来的机器人，到第八分钟仍然能正常运行。高手可以判断：

```js
if (game.phase === "CORE_OPEN") {
    // 去中心抢高价值目标
}
```

但这只是策略优化，不是“不改代码就不能玩”。

地图上的资源刷新、Boss 警告之类可以存在，但不要再称为“阶段”，也不要修改基础规则。

---

# 二、地图：我建议做成“八辐轮盘”

64 人最适合这种拓扑：

```text
                         Spawn A
                           │
                 ╭─────────┴─────────╮
            Spawn H                 Spawn B
               │                       │
          ╭────┴────╮             ╭────┴────╮
          │ 外环资源 │             │ 外环资源 │
          ╰────┬────╯             ╰────┬────╯
               │                       │
          ═════╪═══════ 中 环 ════════╪════
               │                       │
               │     ╔══════════╗      │
               ├─────║          ║──────┤
               │     ║   CORE   ║      │
               │     ║  中央区   ║      │
               ├─────║          ║──────┤
               │     ╚══════════╝      │
               │                       │
          ═════╪═══════════════════════╪════
               │                       │
            Spawn G                 Spawn C
                    ... 另外四个 ...
```

也就是：

```text
8 个出生扇区
   ↓
外环
   ↓
中环
   ↓
8 条径向通路
   ↓
中央核心区
```

不是简单大圆盘，而是一张存在明确“路”的连续二维地图。

---

# 三、为什么用这种地图

64 人直接扔进一个开放场地会出现两个问题：

第一，出生后立刻进入几十个人射程，乱成弹幕游戏。

第二，程序根本没什么策略空间：

```text
nearestEnemy()
→ shoot()
```

就结束了。

八辐结构会自然制造：

```text
小规模遭遇
→ 局部战斗
→ 中环争夺
→ 中央大混战
```

一个玩家平均只会同时处理附近几台机器人。

这对人和程序都舒服很多。

---

# 四、地图实际上分三层

建议尺寸先以约 `160m × 160m` 为参考，之后根据实测调。

### 外环：低风险区

大致距地图中心：

```text
55m ~ 80m
```

主要包含：

- 8 个出生区域；
- 少量 Energy Core；
- 较宽路线；
- 较少死角；
- 较多掩体。

小白出生后不会马上遭到十个人围殴。

机器人写成：

```python
move_to(nearest_core())
```

也能在这里活一阵。

---

### 中环：主要常规战区

大概：

```text
30m ~ 55m
```

这里应该是整局大部分时间真正打架的地方。

放：

- 4～8 个 Uplink；
- 大部分资源；
- 掩体；
- 环形道路；
- 径向通道交叉口。

中环必须能“绕”。

例如：

```text
          ┌────墙────┐
──────────┘          └──────────
         ↖            ↗

         🤖    🤖

──────────┐          ┌──────────
          └──────────┘
```

所以面对敌人不一定只有：

> 前进 / 后退。

还可以：

> 绕左边、绕右边、隔墙逃跑、堵路、伏击。

这马上给路径规划和策略程序留下空间。

---

### 中央核心区：后半场高风险区

前四分钟物理关闭：

```text
╔══════════════╗
║   LOCKED     ║
║              ║
║     CORE     ║
║              ║
╚══════════════╝
```

4:00：

```text
CORE UNLOCKED
```

八个入口同时打开。

中央出现：

- 高价值资源；
- 主 Uplink；
- 大量得分机会。

于是原本散落整张地图的玩家会自然向中央汇集。

不需要安全区毒圈。

也不需要硬把所有人赶进去。

想苟的人仍然可以在外围活动，只是中央收益明显高。

---

# 五、地图设计有几个硬规则

我会明确写入地图规范：

**不做长死路。**

任何重要区域至少两个出口，否则程序特别容易卡死。

**不做只有一条入口的核心区域。**

64 人会直接堵门。

**出生区不能从远处直接射进去。**

需要墙或者折线路径隔开出生区域。

**地图路径尽量形成环。**

也就是：

```text
A → B → C
↑       ↓
F ← E ← D
```

而不是：

```text
A → B → C → dead end
```

环状拓扑既适合玩家，也适合自动寻路。

---

# 六、障碍物第一版只需要一种

不要马上搞：

```text
草丛
玻璃
可破坏墙
单向门
沼泽
减速区
传送门
熔岩
```

第一版只有：

> **实体墙**

它同时：

- 阻挡机器人；
- 阻挡子弹；
- 阻挡视线。

于是所有人的模型非常统一：

```text
看不见
=
打不到
=
走不过去
```

对小白极其友好。

以后再添加特殊地形。

---

# 七、机器人运动：我建议取消“车头必须朝移动方向”

这里值得改之前设计。

如果机器人像坦克一样：

```text
转向
→ 前进
→ 转炮塔
→ 开枪
```

对新手代码太繁琐。

建议机器人采用**全向底盘 + 独立炮塔**：

```text
              炮塔方向
                  ↑
               ──●──
              ╱     ╲
             │  BOT  │
              ╲_____╱

              ↙  ↓  ↘
             任意移动
```

于是：

```js
moveTo(core.position);
aimAt(enemy.position);
fire();
```

可以同时发生。

手操则天然对应：

```text
WASD       移动
鼠标       瞄准
左键       射击
Space      Dash
右键/E     Shield
```

这是最适合网页游戏的控制方式。

---

# 八、基础移动模型

不要做惯性很强的物理系统。

一点惯性即可，否则小白手感很怪，机器人代码也难写。

建议先从：

```text
最大普通速度       8 m/s
加速度            24 m/s²
机器人半径         0.6m
```

开始测。

机器人之间采用软碰撞。

不能直接穿过去，但也不要出现 20 台机器人卡成一团。

可以做轻微 separation：

```text
🤖🤖🤖🤖

     ↓

🤖 🤖 🤖 🤖
```

墙则硬碰撞。

---

# 九、Dash

Dash 是主要机动技能。

例如：

```text
消耗 Energy      20
冷却             2.5s
持续             0.30s
速度             ~16m/s
无无敌帧
```

注意最后一点。

Dash 是：

> 快速移动。

不是：

> 按一下免疫攻击。

所以高手可以用它预测躲弹，小白也能拿它逃跑。

程序：

```js
if (incomingProjectile && danger) {
    dash(awayFrom(projectile));
}
```

自然形成高阶玩法。

---

# 十、战斗核心：一定使用实体弹丸

不要做：

```text
点击敌人
→ 自动扣血
```

也不要做 hitscan 激光。

应该是真正的 projectile：

```text
🤖 ─────→ • ─────→ 🤖
```

例如初始参考值：

```text
HP               100
Projectile damage 12
Projectile speed  28~32 m/s
Fire interval     250 ms
Effective range   ~24m
```

理论连续命中：

```text
9 发左右击毁
```

大约两秒。

但真实游戏里会：

```text
躲
墙挡
打空
Dash
Shield
```

所以真实 TTK 大概落在 3～6 秒。

我认为这个区间比较合适。

短于两秒，小白甚至不知道自己为什么死。

长于十秒，两个人互射会很拖。

---

# 十一、炮弹一定可以躲

这是手操和编程都好玩的基础。

如果敌人位置为：

```text
p
```

速度：

```text
v
```

弹丸飞行时间：

```text
t
```

高手可以计算：

```text
target ≈ p + v * t
```

于是产生提前量射击。

小白：

> 鼠标往敌人前面点一点。

高手：

> 解拦截方程。

AI：

> 帮我写预测射击。

三类人都能参与同一个机制。

这正是我们需要的设计。

---

# 十二、Energy：统一限制特殊能力

建议：

```text
Energy     100
恢复        10/s
```

普通移动不耗能。

射击：

```text
5 / shot
```

Dash：

```text
20
```

Shield：

```text
持续约 18/s
```

主动增强扫描：

```text
10~15
```

因此：

```text
一直开盾
+
一直 Dash
+
疯狂射击
```

不可能同时成立。

这是整个战斗系统最主要的资源决策。

---

# 十三、Shield 应该有明显取舍

我建议：

> 开盾后受到伤害降低约 65%，但无法射击。

移动速度可以保留 80%左右。

于是它不是第二条 HP：

```text
开盾
→ 扛伤
→ 选择逃跑 / 等机会
```

而不是：

```text
所有聪明机器人永久 shield=true
```

程序就会产生很自然的逻辑：

```python
if hp < 30 and enemy_nearby:
    shield(True)
    move_away(enemy)
else:
    shield(False)
```

非常适合初学者理解。

---

# 十四、`scan()` 我赞成直接近乎免费

我甚至会重新定义这个 API。

不是：

```text
scan()
→ 执行动作
→ 花 Energy
```

而是：

> **服务器每个感知 tick 自动为机器人维护一份 Observation。**

例如 10Hz：

```text
Game simulation     20Hz
Robot observation   10Hz
```

玩家调用：

```js
scan()
```

只是读取：

```text
当前 Observation
```

因此：

```text
Energy cost = 0
Action cost = 0
```

一帧调用十次也不会得到十次真实扫描，只是重复读取同一份数据。

这样：

```js
const state = scan();
```

就应该像读 `self.hp` 一样自然。

---

# 十五、默认感知范围

例如：

```text
普通视觉半径：18m
```

同时受墙遮挡。

于是：

```text
          WALL
🤖  ───── █████ ───── 🤖
```

双方 `scan()` 都看不到对方。

这使掩体真正有意义。

Observation 可以直接提供：

```ts
interface Observation {
    self: Self;

    robots: Robot[];
    projectiles: Projectile[];
    cores: Core[];
    uplinks: Uplink[];

    visibleObstacles: Obstacle[];
}
```

小白不用自己处理空间索引。

---

# 十六、然后额外提供一个真正有成本的 Active Scan

这才值得花 Energy。

比如：

```js
pulseScan()
```

效果：

```text
普通范围      18m
Pulse 范围    32m
Energy        -12
Cooldown      2s
```

但我建议它仍然不能穿实体墙。

否则“墙阻挡视野”规则立刻变复杂。

所以它只是：

> 看得更远。

而不是超能力雷达。

如此一来：

```text
scan()
```

人人随便用；

```text
pulseScan()
```

才是战术能力。

---

# 十七、Uplink 可以比传统占点更适合 FFA

我不太喜欢：

> 在圈里站 20 秒。

64 人会变成肉山。

我建议 Uplink 是一个可以短时间“黑入”的设备：

```text
        ◉ Uplink
```

靠近后：

```text
interact()
```

持续比如：

```text
1.5 秒
```

完成后：

```text
+15 分
```

设备进入：

```text
10 秒 cooldown
```

然后任何人都可以再次抢。

这样玩家的行为是：

```text
冲进去
→ 顶住 1.5 秒
→ 得分
→ 跑
```

而不是蹲在那里一分钟。

机器人程序同样很好写：

```python
uplink = nearest_uplink()

if uplink.ready:
    move_to(uplink)
    interact()
```

---

# 十八、资源也应该有确定性

不要纯随机往地图上撒。

建议地图有固定：

```text
Core Spawn Pad
```

例如：

```text
◇
```

资源会从这些位置刷新。

这样小白知道：

> 这里经常有东西。

高手则可以：

```text
记住刷新点
预测下一轮
规划路线
```

第一阶段外围、中环刷得较多。

第二阶段资源权重开始向中央倾斜。

注意这不是规则变化：

```text
Core 还是 Core。
```

只是：

> 值钱的东西开始更多出现在中央。

---

# 十九、唯一一次转段怎么设计

我建议 4:00 做一个非常明显的演出：

```text
3:50

CENTRAL CORE
UNLOCKING IN 10
```

然后：

```text
3
2
1

████ CORE OPEN ████
```

中央八道门同时打开。

同时：

```text
中央 Mega Core 出现
中央 Uplink 激活
中央资源刷新权重提高
```

除此之外：

```text
HP 不变
伤害不变
API 不变
队伍不变
技能不变
```

所以程序根本不用改。

高手如果愿意，只修改战略：

```js
if (game.coreOpen) {
    moveTo(CENTER);
}
```

---

# 二十、我甚至建议“搭档”从开局持续到结束

不要再拿它做阶段。

64 人开局随机形成：

```text
32 对
```

搭档永久存在整局。

双方：

```text
互相不可伤害
地图上互相可见
共享击杀 Assist
靠得比较近时获得少量协作分
```

但是：

> 不共享 HP，不强制绑在一起。

所以你完全可以不理搭档。

但 UI 会不断提醒：

```text
你的搭档 Alice 正在攻击 Bob
```

程序也能：

```js
partner()
```

这样破冰机制整局稳定存在，不需要一分钟换一次朋友。

我认为这比之前“一会双人、一会四队、一会 Boss、一会 FFA”明显好。

# 最终 v0.2 核心战斗循环

现在已经可以非常清楚地表达：

```text
              免费感知
                 ↓
            Observation
                 ↓
        ┌────────┴────────┐
        ↓                 ↓
      手操              程序
        └────────┬────────┘
                 ↓
       move / aim / fire
       dash / shield
                 ↓
         连续二维机器人战斗
                 ↓
      ┌──────────┼──────────┐
      ↓          ↓          ↓
     打人       抢 Core    黑 Uplink
      └──────────┼──────────┘
                 ↓
                得分
```

地图推动节奏：

```text
0:00

64 人从外围开始
↓
外环搜资源
↓
进入中环
↓
形成局部战斗
↓
玩家开始修改 Bot
↓
──────── 4:00 ────────
中央核心开启
↓
战斗逐渐向中心集中
↓
高价值争夺
↓
8:00 结算
```

我认为这版比前一版明显更稳：**机制八分钟基本不变，所以玩家真有时间写程序；战场本身从分散逐渐收拢，所以又不会八分钟一个节奏。**

下一步最值得继续定数值的其实是两个问题：**视野/射程/地图尺寸之间比例**，以及 **控制 API 到底提供多高层能力**。尤其后者会直接决定“小白五行代码能做到什么”和“大佬还能往上卷多少。**
