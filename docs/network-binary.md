# 紧凑二进制实时网络

## 范围与兼容

方案 2 已将高频快照改为自定义二进制，而不是在 JSON 外面包一层二进制。
原先传输也不是纯 JSON：它是二进制 WebSocket 内的 Protobuf，但快照里的
`map_json` 字段仍反复携带局部地图 JSON。

- 客户端协商 `omb.binary.v1` 后，使用 `0x04` 紧凑快照、`0x05` 有序批帧。
- 上行和低频控制事件继续用 Protobuf；旧客户端不协商则保留 `0x03` 下行。
- 不启用 permessage-deflate，不引入通用压缩依赖。
- 权威模拟、脚本感知、AOI、60Hz 快照节奏不变；量化只发生在网络边界。
- 新客户端在协商握手失败时仅尝试一次不带子协议的旧格式连接，支持旧服务端。

逐字节布局和范围见 [binary-v1.md](../protocol/binary-v1.md)。位置采用厘米级
有符号 16 位定点数，方向为 16 位整圈角度，实体通过变化掩码发送；
静态昵称、颜色和 Self 状态不再每帧重复发送。倒计时和 AI 剩余轮次保留
32 位，覆盖 24 小时热身及已有配额配置。非有限数与溢出报错，不静默截断。

紧凑路径不序列化或解析局部地图 JSON。客户端使用 MapBootstrap 的静态地图
与当前可见资源 ID 重建 Uplink/血包元数据；脚本仍消费原有感知，不扩大
可见范围，观战者仍保留完整地图。血包仅在状态变化、首次可见或 full 时发送。

## 消息数量与一致性

批处理减少的是实际 WebSocket 消息数，不是删除可靠玩法事件：

- writer 最多收集 1ms、64 个子消息或 64KiB，不增加一个模拟 tick 的等待。
- 单个子消息不包装；超出批容量的消息留到下一次，可靠队列顺序不变。
- MapBootstrap 为屏障；脚本日志保留独立低优先级，不参与可靠批处理。
- 大脚本历史等单独 Protobuf 控制帧保留原有解码行为，不施加新的快照大小上限，
  避免 32 份源码的历史被误当作超大实时帧丢弃；上行提交仍为 64KiB。
  AI 生成源码历史尚无聚合字节上限，其应用层分块/限量仍是后续独立问题。
- 编码基线在实际 writer 交付顺序中更新，而非入队时更新。旧局 epoch、
  被可靠 full 超过的旧 lossy 快照不再污染新基线，同 tick full 重同步仍可交付。
- `base_tick` 缺口只交付头部并触发已有 ResyncRequest，等待 full，绝不猜补实体。
- 整帧或整批验证成功后才提交解码状态，畸形后半批不会泄漏前半批消息。

## 2026-10-17 本地验证

环境：Windows/amd64、Core Ultra 9 285H、Go 1.25.0；服务端 GOMAXPROCS=8、
压测端为 4，GOGC=400。同机 200 个真实 WS 连接，50% 提交内置脚本，
30Hz 输入并启用瞄准/开火轴。每种格式单独启动新服务运行 25 秒，无通用压缩。
应用载荷包含帧类型，不包含 WS/TLS/TCP/IP 头、重传和公网链路成本。

| 指标 | 旧 Protobuf | 紧凑二进制 |
| --- | ---: | ---: |
| 全程平均下行载荷 | 300.2 Mbps | 54.6 Mbps |
| 全程平均 WS 消息 | 32,844/s | 22,031/s |
| 全程平均解批后应用消息 | 32,748/s | 31,227/s |
| t+20s tick | 1149 | 1116 |
| t+20s tick avg / p95 | 12.17 / 18.63ms | 12.43 / 17.74ms |
| 快照缺口 / lossy 丢弃 / reliable 满断开 | 0 / 0 / 0 | 0 / 0 / 0 |

该组运行中应用载荷约减少 82%，WS 消息约减少 33%；在同一个二进制运行内，
WS 消息比解批后应用消息少约 29%，这是批处理本身的效果。独立地图种子和
运行轨迹不同，不能将全部跨运行差异归因于协议。两次都不是稳定 60Hz
的正式局容量证明，最终上线仍需目标机长局、复杂脚本与资源峰值验证。

同一段既有开火抓包的离线复放：20 个连接、12,000 条消息，其中 4,295 条
快照。仅替换快照、不合批且不压缩，总载荷约从 13.57MB 降至 2.52MB
（保留 18.6%）；快照平均约从 3,072B 降至 499B。抓包起于中局，每流首个
快照仅人为标为 full 作为测量种子，不是完整初始化，也没有补造缺失昵称。
因此该数据证明同序列字节收益，不代表首连或任意正式局的精确比例。

Node 24 同序列解码测试（3 轮预热、7 轮测量，中位数）：紧凑解码约
13.0 微秒/快照，Protobuf 约 22.2 微秒，Protobuf 加局部 JSON 解析约
26.1 微秒。该计时包含二进制基线维护和应用对象构造，但不是浏览器整帧耗时。
Go 编码器为保证事务性仍存在基线复制和临时分配，单独编解码微基准并未
证明比 Protobuf 更快；低网络成本已验证，服务端低解析/编码开销不可一概而论。

本地原始日志与测量脚本位于忽略目录 `.artifacts/network-binary-20261017-0112/`，
不作为生产承诺。旧 `omb-load` 的 Mbps 标签漏乘 8；历史的“28 Mbps”应读作
约 224 Mbps，不能直接拿旧标签与本次结果比较。

## 复测

服务端使用测试配置关闭 AI 外部调用和认证，并设置 `OMB_MAX_PLAYERS=200`，
不要直接对线上服务执行。构建后分别运行：

```sh
go build -o server/omb-load ./server/cmd/omb-load
server/omb-load -addr 127.0.0.1:27182 -n 200 -scripts 0.5 -input 30 -battle -legacy -duration 25s
server/omb-load -addr 127.0.0.1:27182 -n 200 -scripts 0.5 -input 30 -battle -duration 25s
```

每次使用干净的新服务或隔离房间；报告真实快照速率、tick 和丢帧，不要把模拟
降速带来的低流量当作协议收益。输出的 `ws_msg_s` 是 WS 帧率，`app_msg_s`
是解批后的应用消息率，`down` 已按 bits/s 计算。

真实服务端到 TypeScript world 的非 UI 集成测试：

```sh
go build -o server/omb.exe ./server/cmd/omb
# Set OMB_BINARY to the absolute path of the just-built executable.
pnpm --dir client exec tsx scripts/binary-network-check.mjs
```

脚本只启动任务自有的本地服务，退出时关闭连接并停止该服务；覆盖紧凑玩家、
旧格式玩家、观战者、full 重同步、24 小时倒计时和大脚本历史。跨语言 golden、
畸形帧与每字节截断回归分别在 Go wire 和 TS binary 测试中维护。
