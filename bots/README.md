# bots/ — 实战脚本

本目录存放可直接投入对局的完整脚本。**使用方式：复制文件全文 → 游戏内编辑器（TS 模式）粘贴 → 提交 → 开启辅助（Assist）。** 编辑器会把 TS 编译为 JS 再提交，`@omb/bot-api` 的类型由编辑器内置，无需额外配置。

## oracle.ts — Oracle（当前主力脚本）

单文件三合一：定向路线规划 + 线性血量权重 + 二阶提前量火控。

### ① 路线规划（Orienteering / 定向问题）

把全图可见的 `cores` / `uplinks` / `healthPacks` 统一抽象为带权节点（权重 = 得分值：Core +10、Mega +25、Uplink +15、主桩 +25、血包为效用折算分），每 0.5s 求解一次：

$$\max \; \sum_i v_i \;-\; \lambda \cdot \text{里程} \quad \text{s.t. 总里程} \le \text{MAX\_ROUTE\_M}$$

- **精确求解**：节点 ≤ 9 个时用 Held-Karp 状压 DP（`dp[mask][last]`），O(2ⁿ·n²) ≈ 4 万次转移；
- **超限预选**：节点更多时按性价比 `value/(dist+8)` 预选 9 个再求解（34 个 Core 垫全图，中后期可能超限）；
- **λ 汇率**：每多走 1 米需要 ≥ 0.25 分才值得绕路，是"路线尽量短、得分尽量高"的唯一旋钮；
- **站桩折算**：Uplink 需原地站 8s，按 `UPLINK_STAND_COST_M=16` 折算为附加里程参与决策；
- 空路线（0 分）是合法基线——不值得出门时不出门。

执行层消费路线时：捡 Core / 压血包靠身体接触自动完成；Uplink 进入交互半径后转入站桩状态机（见下）。

### ② 血包线性权重

`v(hp) = K·(1 − hp/100)`，K=30：满血恒 0（永不误触发），hp<67 压过 Core(+10)、hp<50 压过 Uplink(+15)。血包与得分目标在同一个 DP 里竞争，因此"顺路补血"会自然发生。

另有危急兜底：hp < 22 时无视路线直奔最近可用血包；站桩中血线告急会打断站桩。

### ③ 二阶提前量火控

目标运动按**恒加速度模型** `X(τ) = P + V·τ + ½A·τ²`：

- 加速度由相邻帧速度差分（÷1/60s）+ EMA（α=0.35）估计，幅度截断 30 m/s²（服务器上限 24，滤掉 dash/撞击尖峰）；速度 >8.5 m/s 判定 dash，按匀速处理；
- 拦截时间满足 `τ = τ₀ + |X(τ)−S|/v_b`（τ₀=1 tick 管线延迟，S 含自机速度前移），用**不动点迭代**解出（8 次，目标径向速度 < 弹速时收敛）；
- 开火闸门：命中点 ≤ 16.5m（无散布区）、拦截时长 ≤ 1s、弹道未被墙/锁区遮挡（Liang-Barsky 线段-AABB + 线段-圆检测）、能量 ≥ 15（近距除外）；
- 站桩期间只预瞄不开火（`canHack` 要求本 tick 无 fire 意图），近敌 ≤ 12m 才打断自卫。

### 验证状态

- `oracle.test.ts`：30 个用例（DP 最优性/预算/顺序、提前量与解析解/数值求根对比、节点抽象、执行器状态机全场景）；
- `tsc -p bots/tsconfig.json` strict 通过（`@omb/bot-api` paths 映射）；
- 「编辑器 TS 编译 → 客户端清理 → 服务端 strip」全链路模拟后为合法 JS（顶层 `tick` 入口）；
- 真实 goja runtime 冒烟：站桩节奏 479/480 tick 精确；9 节点满配 DP 峰值 4.1ms / 均值 0.13ms（预算 10ms）。

### 已知取舍

- 节点 > 9 时预选是贪心近似（丢弃低性价比节点）；
- 里程用欧氏距离估算，墙体绕行会让实际路程略长；
- `CORE_ZONE_R=28`、`MEGA_PAD_IDS={29,30}` 与 mapgen GeneratorVer 6 绑定，mapgen 变更时需同步；
- 没有做走位躲弹、护盾和 dash 管理（能量全部留给开火），属于后续增强点。
